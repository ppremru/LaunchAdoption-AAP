**1. AAP Host Verification**

Assumptions:
* Executed on the AAP host CLI.
* Windows/AD team has provisioned two dedicated Active Directory service accounts set to "Password Never Expires":
  * **LDAP Bind Account (`svc_aap_bind`):** Used by the AAP host for Web UI domain authentication. Requires `Domain Users` group membership and `Read` permissions on user OUs.
  * **Automation Account (`ansible_svc`):** Used by the Execution Environment container to manage Windows endpoints. Requires `Domain Users` group membership, AES 128/256-bit encryption enabled in AD, and Local Administrator rights on target Windows servers.

Run these commands on the AAP host CLI to verify network access and credentials before configuring AAP or building containers:

```bash
# Verify host network access to Active Directory (Ports 636, 88) and target Windows hosts (Port 5986)
nc -zvw3 dc01.yourdomain.com 636
nc -zvw3 dc01.yourdomain.com 88
nc -zvw3 win01.yourdomain.com 5986

# Verify LDAP Bind account credentials, password status, and OU search access from host OS
ldapsearch -x -H ldaps://dc01.yourdomain.com:636 \
  -D "CN=svc_aap_bind,OU=ServiceAccounts,DC=yourdomain,DC=com" \
  -w 'Password' -b "OU=Users,DC=yourdomain,DC=com" "(sAMAccountName=jdoe)"

# Verify host DNS resolution and Kerberos ticket issuance for the Automation Account
kinit ansible_svc@YOURDOMAIN.COM && klist
```

**2. AAP Host CA Certificate Trust**

Assumptions:
* Executed with `root` or `sudo` privileges on the AAP host CLI.
* Enterprise CA certificate files (`corp_root_ca.crt` and `corp_intermediate_ca.crt`) are transferred and staged on the local filesystem in PEM format.
* Standard RHEL base packages (`ca-certificates` containing `update-ca-trust`, and `openssl`) and default system paths are present.

Import enterprise Root and Intermediate CA certificates into the AAP host OS trust store to enable system-level TLS trust for LDAPS web UI authentication and secure WinRM connections:

```bash
# Copy enterprise CA certificates to the system anchor store
cp corp_root_ca.crt /etc/pki/ca-trust/source/anchors/
cp corp_intermediate_ca.crt /etc/pki/ca-trust/source/anchors/

# Update the system-wide CA trust store
update-ca-trust extract

# Verify TLS handshake to Domain Controller against the updated trust store
openssl s_client -connect dc01.yourdomain.com:636 -CAfile /etc/pki/tls/certs/ca-bundle.crt
```

**3. AAP Controller Settings Files**

Assumptions:
* Executed via the AAP Controller Web UI (`Settings -> System -> LDAP/SAML`) or applied programmatically via Controller API / Infrastructure as Code (`infra.controller_configuration`).
* Service accounts and AD OUs defined in Step 1 exist and are reachable.
* Host-level CA trust configured in Step 2 is active.

These JSON configurations control human user authentication and team/role assignments for the AAP Web UI:

* **File 1: LDAP Authentication (`ldap_config.json`)**  
  Setting `LDAP_OPT_REFERRALS: 0` prevents domain referral timeouts in multi-domain setups.

  ```json
  {
    "LDAP_SERVER_URI": "ldaps://dc01.yourdomain.com:636 ldaps://dc02.yourdomain.com:636",
    "LDAP_BIND_DN": "CN=svc_aap_bind,OU=ServiceAccounts,DC=yourdomain,DC=com",
    "LDAP_BIND_PASSWORD": "<service_account_password>",
    "LDAP_START_TLS": false,
    "LDAP_REQUIRE_GROUP_TYPE": "ActiveDirectoryGroupType",
    "LDAP_OPT_REFERRALS": 0,
    "LDAP_USER_SEARCH": [
      "OU=Users,DC=yourdomain,DC=com",
      "SCOPE_SUBTREE",
      "(|(sAMAccountName=%(user)s)(userPrincipalName=%(user)s))"
    ],
    "LDAP_USER_ATTR_MAP": {
      "first_name": "givenName",
      "last_name": "sn",
      "email": "mail"
    }
  }
  ```

* **File 2: Role-Based Group Mapping (`rbac_config.json`)**  
  Maps AD Security Groups to AAP roles. Setting `"remove": true` automatically revokes access when users leave AD groups.

  ```json
  {
    "LDAP_GROUP_SEARCH": [
      "OU=Groups,DC=yourdomain,DC=com",
      "SCOPE_SUBTREE",
      "(objectClass=group)"
    ],
    "LDAP_GROUP_TYPE_PARAMS": {
      "name_attr": "cn"
    },
    "LDAP_ORGANIZATION_MAP": {
      "Default": {
        "users": "CN=SG_AAP_Default_Users,OU=Groups,DC=yourdomain,DC=com",
        "admins": "CN=SG_AAP_Default_Admins,OU=Groups,DC=yourdomain,DC=com",
        "remove_users": true,
        "remove_admins": true
      }
    },
    "LDAP_TEAM_MAP": {
      "Windows Engineering": {
        "organization": "Default",
        "users": "CN=SG_Windows_Admins,OU=Groups,DC=yourdomain,DC=com",
        "remove": true
      }
    },
    "LDAP_USER_FLAGS_BY_GROUP": {
      "is_superuser": [
        "CN=SG_AAP_System_Admins,OU=Groups,DC=yourdomain,DC=com"
      ]
    }
  }
  ```

* **File 3: SAML / SSO Configuration (`saml_config.json`)**  
  Configures SAML Single Sign-On using Identity Provider group Object GUIDs.

  ```json
  {
    "SOCIAL_AUTH_SAML_SP_ENTITY_ID": "[https://aap.yourdomain.com/sso/metadata/saml/](https://aap.yourdomain.com/sso/metadata/saml/)",
    "SOCIAL_AUTH_SAML_ENABLED_STRATEGIES": {
      "entra_id": {
        "entity_id": "[https://sts.windows.net/00000000-0000-0000-0000-000000000000/](https://sts.windows.net/00000000-0000-0000-0000-000000000000/)",
        "url": "[https://login.microsoftonline.com/00000000-0000-0000-0000-000000000000/saml2](https://login.microsoftonline.com/00000000-0000-0000-0000-000000000000/saml2)",
        "x509cert": "<CONTENTS_OF_IDP_SIGNING_CERTIFICATE>",
        "attr_user_permanent_id": "[http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier](http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier)",
        "attr_username": "[http://schemas.microsoft.com/ws/2005/05/identity/claims/name](http://schemas.microsoft.com/ws/2005/05/identity/claims/name)"
      }
    },
    "SOCIAL_AUTH_SAML_TEAM_MAP": {
      "Windows Operations": {
        "organization": "Default",
        "users": {
          "attr": "[http://schemas.microsoft.com/ws/2008/06/identity/claims/groups](http://schemas.microsoft.com/ws/2008/06/identity/claims/groups)",
          "value": ["aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee"],
          "remove": true
        }
      }
    }
  }
  ```

**4. Execution Environment Build & Container Validation**

Assumptions:
* Executed on a container build system or AAP host with `ansible-builder` (v3+) and `podman` installed.
* Network access is available to Red Hat Ecosystem Catalog (`registry.redhat.io`) and your organization's container registry.
* Enterprise CA certificates and domain Kerberos details are available in the local directory.

These files and commands define, assemble, and validate the custom Execution Environment container used for Windows and Active Directory automation:

* **File 1: Container Build Definition (`execution-environment.yml`)**

  ```yaml
  version: 3
  images:
    base_image:
      name: registry.redhat.io/ansible-automation-platform-24/ee-supported-rhel9:latest

  dependencies:
    python:
      - pywinrm[kerberos]
      - requests-kerberos
      - gssapi
    system:
      - krb5-workstation
      - krb5-libs
      - ca-certificates

  additional_build_steps:
    append_final:
      - COPY krb5.conf /etc/krb5.conf
      - COPY corp_root_ca.crt /etc/pki/ca-trust/source/anchors/
      - COPY corp_intermediate_ca.crt /etc/pki/ca-trust/source/anchors/
      - RUN update-ca-trust extract
  ```

* **File 2: System Kerberos Configuration (`krb5.conf`)**  
  Domain realms **must be written in ALL CAPS**.

  ```ini
  [libdefaults]
      default_realm = YOURDOMAIN.COM
      dns_lookup_realm = false
      dns_lookup_kdc = true
      ticket_lifetime = 24h
      renew_lifetime = 7d
      forwardable = true

  [realms]
      YOURDOMAIN.COM = {
          kdc = dc01.yourdomain.com:88
          kdc = dc02.yourdomain.com:88
          admin_server = dc01.yourdomain.com
      }

  [domain_realm]
      .yourdomain.com = YOURDOMAIN.COM
      yourdomain.com = YOURDOMAIN.COM
  ```

* **Build & Validation Commands**

  ```bash
  # 1. Build container image using execution-environment.yml in current directory
  ansible-builder build --tag [my-registry.com/automation/windows-kerberos-ee:latest](https://my-registry.com/automation/windows-kerberos-ee:latest)

  # 2. Authenticate and push image to enterprise registry
  podman login my-registry.com
  podman push [my-registry.com/automation/windows-kerberos-ee:latest](https://my-registry.com/automation/windows-kerberos-ee:latest)

  # 3. Launch container shell interactively to test image contents
  podman run --rm -it [my-registry.com/automation/windows-kerberos-ee:latest](https://my-registry.com/automation/windows-kerberos-ee:latest) /bin/bash

  # 4. Acquire test ticket and verify Python module bindings inside container
  kinit ansible_svc@YOURDOMAIN.COM && klist
  python3 -c "import winrm; print(winrm)"

  # 5. Exit container shell
  exit
  ```

**5. Inventory & Playbook Configuration**

Assumptions:
* Executed within your Ansible Git repository connected to AAP Controller.
* Target Windows hosts are defined by their **Fully Qualified Domain Names (FQDNs)** in the inventory (Kerberos fails if IP addresses or short names are used).
* Service account credentials (`ansible_svc`) are managed via AAP Machine Credentials or Ansible Vault.

These files configure WinRM connection parameters over Kerberos and define a baseline playbook to verify Windows host management:

* **File 1: Windows Group Variables (`group_vars/windows.yml`)**  
  Configures WinRM HTTPS (Port 5986) over Kerberos.

  ```yaml
  ---
  ansible_connection: winrm
  ansible_port: 5986
  ansible_winrm_transport: kerberos
  ansible_winrm_realm: YOURDOMAIN.COM
  ansible_winrm_server_cert_validation: validate
  ansible_user: "ansible_svc@YOURDOMAIN.COM"
  ```

* **File 2: Windows Connection Test Playbook (`test_windows_connectivity.yml`)**  
  Validates WinRM connectivity and AD authentication from inside the container to target endpoints.

  ```yaml
  ---
  - name: Test Windows WinRM and Active Directory Authentication
    hosts: windows
    gather_facts: true

    tasks:
      - name: Ping target Windows hosts
        ansible.windows.win_ping:

      - name: Retrieve target system domain information
        ansible.windows.win_powershell:
          script: |
            [System.Net.Dns]::GetHostByName(($env:COMPUTERNAME)).HostName
            $env:USERDNSDOMAIN
  ```

**6. AAP Controller Execution & Job Template Verification**

Assumptions:
* Executed via the AAP Controller Web UI or API.
* The Execution Environment container image built in Step 4 is pushed to an accessible registry.
* The Git repository containing inventory and playbooks from Step 5 is synced to AAP Controller as a Project.
* Service account credentials (`ansible_svc@YOURDOMAIN.COM`) are stored securely as a Machine Credential in AAP.

This step registers the custom Execution Environment in AAP Controller and runs a test Job Template to verify end-to-end Active Directory and WinRM integration:

* **Step 6.1: Register Execution Environment in AAP**
  1. Navigate to **Execution Environments** -> **Add**.
  2. Set **Name**: `Windows Kerberos EE`.
  3. Set **Image**: `my-registry.com/automation/windows-kerberos-ee:latest`.
  4. Set **Pull**: `Always` (or `Only when missing`/`Always pull` per registry policy).
  5. Attach Container Registry credentials if the registry requires authentication.

* **Step 6.2: Configure Machine Credential**
  1. Navigate to **Credentials** -> **Add**.
  2. Set **Name**: `AD Automation Account (ansible_svc)`.
  3. Set **Credential Type**: `Machine`.
  4. Set **Username**: `ansible_svc@YOURDOMAIN.COM` (must include domain/realm).
  5. Set **Password**: `<service_account_password>`.
  6. Leave SSH Key and privilege escalation fields blank.

* **Step 6.3: Configure & Run Job Template**
  1. Navigate to **Templates** -> **Add** -> **Add job template**.
  2. Set **Name**: `Test - Windows WinRM Connectivity`.
  3. Select **Inventory**: Your target Windows host inventory.
  4. Select **Project**: Synced Git repository containing `test_windows_connectivity.yml`.
  5. Select **Execution Environment**: `Windows Kerberos EE`.
  6. Select **Playbook**: `test_windows_connectivity.yml`.
  7. Select **Credentials**: `AD Automation Account (ansible_svc)`.
  8. Click **Save** and **Launch**.
  9. Confirm job execution logs show `SUCCESS` with valid WinRM ping responses and Active Directory domain facts returned.
